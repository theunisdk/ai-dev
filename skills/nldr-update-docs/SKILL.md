# NLDR Update Docs

Bring existing documentation in sync with the current codebase while preserving manual refinements. Delta-driven: only change what's wrong, missing, or orphaned.

## Depth detection (first step, always)

Read `docs/INDEX.md` frontmatter:

- `docs-level: light` → the doc set is README.md + a self-contained INDEX.md. Maintain exactly that — do NOT add per-table/per-system docs.
- `docs-level: full` → hierarchical doc set. Maintain existing structure and depth.
- **No marker** → infer the level from the structure (single self-contained INDEX = light; INDEX linking to topic docs = full), add the marker as part of the update, and tell the user what you inferred.
- **No docs/INDEX.md at all** → stop; recommend `nldr-gen-docs-light` or `nldr-gen-docs` instead.

## Process

### Phase 1: Audit existing docs
Read every file in `docs/`, plus `README.md`, `CLAUDE.md`, `AGENTS.md`, `.cursorrules` if present. Build an inventory of documented systems, collections, features, concepts, and every source-file path referenced.

### Phase 2: Analyze the codebase
Scan current structure, data layer (schemas/models/triggers/migrations), domains, business rules, dependencies.

### Phase 3: Gap analysis — present BEFORE changing anything
Categorize findings:

- **Stale** — documented things that changed (renamed files, modified rules, changed structures)
- **Missing** — new systems/collections/rules with no docs
- **Orphaned** — docs for things that no longer exist
- **Broken references** — paths pointing to moved/renamed/deleted code or docs
- **Structural** — missing INDEX entries, broken navigation
- **Over-documentation** — docs exceeding the project's level (e.g. per-table docs in a light project, docs duplicating an explicit schema file, doc volume disproportionate to code size). Propose deletion/consolidation — shrinking the doc set is a valid and expected outcome.

**Present this summary to the user and wait for their go-ahead before making changes.** (Exception: if the user explicitly asked to run non-interactively, apply and report instead.)

### Phase 4: Apply updates
- **Existing docs:** preserve structure; update only stale sections; keep accurate manual refinements; fix references.
- **New docs:** follow the level and format of the existing set.
- **Orphaned/over-docs:** delete, and remove their INDEX entries.
- **Always check:** `docs/INDEX.md` (navigation current), `README.md`, and in full mode `docs/tech-stack.md` + `docs/improvements.md` (refresh improvements completely — it goes stale fastest).

### Phase 5: Validate, then commit
1. Every doc linked from INDEX.md exists; every existing doc is linked.
2. All file-path references point to files that exist.
3. Level marker present and correct.

Commit with a message describing what was updated and why.

## Rules

- **Preserve manual refinements** — never regenerate content that's still accurate.
- **Focus on the delta** — don't rewrite correct docs.
- **CLAUDE.md is in scope** — if it contradicts the codebase (stale commands, wrong claims like "no tests"), fix it.
- Reference source files; don't copy code into docs.

## Common mistakes

- Regenerating everything from scratch (destroys manual refinements — that's what the gen skills are for).
- Only adding docs, never deleting — doc sets should shrink when the code does, or when they were over-generated.
- Skipping the gap-analysis presentation and just changing things.

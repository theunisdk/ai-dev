# NLDR PR Docs

Review the code changes in a pull request (or current branch diff vs the base branch) and update project documentation to match. Designed to run headlessly: never ask questions, make the updates, report what was done.

## Ground rules

- **Never ask for confirmation.** Assess, update, commit, summarize. (CI has no one to answer.)
- **Idempotent.** If docs already reflect the diff — or the diff itself is docs-only — state that and exit with NO changes. This is what stops CI retrigger loops.
- **Scope = the PR diff only.** This is not a full doc sync; don't fix unrelated staleness (that's `nldr-update-docs`). Exception: a broken reference you'd otherwise create.
- **Match the doc level.** Read `docs-level` from `docs/INDEX.md` frontmatter. Light → only README.md and INDEX.md are candidates for updates. Full → the hierarchical set. No docs/INDEX.md at all → report that docs aren't set up (suggest `nldr-gen-docs-light`) and exit without changes.

## Process

### 1. Get the diff
In CI or on a checked-out PR branch: `git diff <base>...HEAD` plus the list of added/deleted/renamed files. Identify the base from the PR context or default branch.

### 2. Categorize the changes
New feature/system · changed business rules or validation · data-layer changes (new tables/collections, schema or trigger changes) · changed flows/workflows · removed features · refactors/renames · dependency changes · config/deployment changes · bug fixes · tests only · cosmetic only.

### 3. Assess doc impact

| Impact | Change types |
|---|---|
| **Always update** | New/changed collections or schemas; new systems or major features; changed business rules, state transitions, data flows, authz/security model; removed features; renamed/moved files referenced in docs; tech-stack-affecting dependency changes |
| **Usually update** | New/changed API endpoint behavior; modified workflows; changed error behavior; deployment-affecting config |
| **Rarely update** | Bug fixes (unless they reveal an undocumented rule); behavior-preserving refactors; tests; cosmetic changes |

No impact → output a one-line assessment ("Tests and formatting only — no doc changes needed") and stop.

### 4. Apply updates
- Existing docs: preserve structure; update only sections the diff affects; fix references the diff broke.
- New systems/collections (full mode): add docs following the existing set's format; register in INDEX.md.
- Removed features: delete their docs; remove INDEX entries.
- Always check: `docs/INDEX.md`, `README.md`; full mode also `docs/tech-stack.md`, `docs/architecture.md`, `docs/improvements.md`.
- Respect the philosophy: business rules and "why", no code examples, reference file paths.

### 5. Validate and commit
1. INDEX links and file-path references valid; level marker intact.
2. Commit doc changes to the PR branch with message: `docs: update for <short PR summary>`.
3. Output a summary: what was updated and why, what was added/removed. In CI this becomes the job log / PR comment.

## Common mistakes

- Asking "should I proceed?" — never; this must run unattended.
- Doing a full doc audit instead of staying on the diff.
- Committing when nothing changed (creates CI loops).
- Adding per-table docs to a light project because the PR touched the DB — light stays light; note in the summary if the project seems to have outgrown light mode.
